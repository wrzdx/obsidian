## 1. Что такое Search

### Information Need vs Query

**Information Need** — реальная потребность пользователя.

Пример:

> Я студент, хочу за 5 минут понять как работают вакцины.

**Query** — то, что пользователь вводит в поиск.

```text
how vaccines work
```

Проблема:

* пользователь теряет контекст;
* средний запрос ≈ 2–3 слова;
* поисковик пытается восстановить реальное намерение по очень слабому сигналу.

---

## 2. Relevance

Релевантность не бинарна.

Шкала:

```text
Perfect
Excellent
Good
Fair
Bad
```

Поэтому поиск — это задача ранжирования, а не фильтрации.

---

## 3. Search vs Database

### Database

```sql
SELECT *
FROM users
WHERE age > 18
```

Характеристики:

* точный ответ;
* порядок не важен;
* легко проверить корректность.

### Search

Запрос:

```text
best vaccine explanation
```

Характеристики:

* ответ субъективен;
* результат — упорядоченный список;
* важен порядок документов.

---

## 4. Search vs Recommendation

### Search (Pull)

Есть явный запрос.

```text
buy iphone
```

### Recommendation (Push)

Запроса нет.

Система сама угадывает интерес пользователя.

Примеры:

* TikTok
* YouTube
* Netflix

Общая схема:

```text
Candidate Generation
        ↓
      Ranking
```

# Lexical Gremlin

Главная проблема поиска — несовпадение слов.

## Synonymy

Одинаковый смысл, разные слова.

```text
couch ↔ sofa
```

Потеря Recall.

Релевантный документ не найден.

---

## Polysemy

Одно слово — несколько значений.

```text
jaguar
```

Может означать:

* животное;
* машину;
* ОС.

Потеря Precision.

Появляются нерелевантные результаты.

---

## Vocabulary Problem

Исследование Furnas (1987):

Два человека используют одинаковое слово для одного объекта менее чем в 20% случаев.

Вывод:

Совпадение слов ≠ совпадение смысла.

---

# Precision и Recall

## Precision

Доля найденных документов, которые действительно релевантны.

```text
Precision =
Relevant Retrieved
------------------
Retrieved
```

Высокая precision → мало мусора.

---

## Recall

Доля всех релевантных документов, которые удалось найти.

```text
Recall =
Relevant Retrieved
------------------
All Relevant
```

Высокий recall → мало пропущенных документов.

# Масштаб проблемы

## Размер веба

Порядок:

```text
10^12 документов
```

---

## Новые запросы

Каждый день:

```text
≈15% запросов никогда не встречались раньше
```

Следствие:

Нельзя заранее сохранить ответы на все запросы.

---

## Закон Ципфа (Zipf)

Есть:

### Head

Частые запросы

```text
youtube
weather
facebook
```

### Long Tail

Редкие запросы

```text
error 0x80070643
```

Вывод:

Нельзя запомнить все запросы.

Нужно уметь обобщать.

# История поиска

## TF

Luhn (1958)

Частота слова в документе.

---

## IDF

Spärck Jones (1972)

Редкие слова информативнее частых.

---

## TF-IDF

```text
TF × IDF
```

Классическая мера важности слова.

---

## BM25

Robertson & Walker (1994)

Улучшенный TF-IDF.

До сих пор используется как базовый retriever.

---

## Word2Vec

Mikolov (2013)

Слова становятся векторами.

```text
king - man + woman ≈ queen
```

---

## Dense Retrieval

2019+

Примеры:

* SBERT
* DPR

Идея:

Документы и запросы кодируются в векторы.

Синонимы оказываются рядом в пространстве.

---

## RAG

Lewis et al. (2020)

```text
Retriever
     ↓
Generator (LLM)
```

LLM отвечает на основе найденных документов.

---

# Retrieval Cascade

Главная идея:

Нельзя применять дорогую модель ко всем документам.

Используется каскад.

```text
Corpus (~10^9)
      ↓
Retrieval (~10^3)
      ↓
Ranking (~10^2)
      ↓
Re-ranking (~10)
```

---

## Retrieval

Инструменты:

* BM25
* ANN

Цель:

```text
Max Recall
```

---

## Ranking

Инструменты:

* Learning To Rank
* GBDT

Цель:

Уточнить порядок документов.

---

## Re-ranking

Инструменты:

* Cross Encoder
* BERT

Цель:

```text
Max Precision@K
```

---

## Важное правило

Первый этап задаёт потолок качества.

Если retrieval потерял документ:

```text
Никакой re-ranker его уже не вернёт.
```

Поэтому:

```text
Recall покупается рано.
Precision полируется поздно.
```

# Training-Serving Skew

Проблема:

Модель обучалась на одних фичах,
а в проде получает другие.

Следствие:

Качество падает без ошибок.

Решение:

```text
Feature Store
```

Единый источник признаков.

# Data Problems

## Covariate Shift

Меняется:

```text
P(x)
```

Не меняется:

```text
P(y|x)
```

Пример:

Новый сезон → другие запросы.

---

## Concept Drift

Меняется:

```text
P(y|x)
```

Пример:

```text
corona
```

2019 → пиво

2020 → вирус

---

## Data Leakage

Будущая информация попала в обучение.

Ложный рост качества.

---

## Label Delay

Правильная метка приходит поздно.

---

## Simpson's Paradox

Общая метрика растёт,
но все сегменты ухудшаются.

---

# Latency Budget

Типичный SLA:

```text
p99 < 200 ms
```

Пример:

```text
API         3 ms
Retrieve   35 ms
Rank       90 ms
Serve       4 ms
----------------
Total     134 ms
```

---

## Главное

Смотреть на:

```text
p99
```

а не на

```text
p50
```

Пользователи чувствуют хвост задержек.

---

# Position Bias

Даже если все результаты одинаково релевантны:

```text
Result #1 получает больше кликов
```

только потому что находится сверху.

Следствие:

```text
Clicks ≠ Relevance
```

---

# Goodhart's Law

Когда метрика становится целью:

```text
Она перестаёт быть хорошей метрикой.
```

Пример:

Оптимизация CTR приводит к кликбейту.
